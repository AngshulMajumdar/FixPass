## Syntax stress test

`scripts/stress_syntax.py`: 600 files, each one of the six reference programs with 1–5 random corruptions: token deletion, insertion, replacement, swap, duplication, smart quotes and other confusable characters, unclosed strings and comments, string literals in single quotes, stray characters, dropped line-final tokens. 570 of them fail to parse (the others happen to remain valid Java and are excluded). Compile stages only, no tests. *Token-exact* means the repaired file has the same token sequence as the original program.

| 1 | 150 | 150 | 150 | 128 | 4 |

| 3 | 106 | 106 | 100 | 37 | 33 |
| 4 | 65 | 65 | 57 | 13 | 27 |

Time per file: median 7.297 s, mean 12.1 s, max 96.547 s (2 vCPU).

Full pipeline with the 10 visible tests on 60 of the files with 1–2 corruptions: 49 pass all visible tests, 48 pass all 40 held-out tests, 42 token-exact, 3 lossy (`benchmarks/syntax_stress/full_pipeline.json`).

## IntroClassJava

`scripts/introclassjava.py`. IntroClassJava (Durieux & Monperrus 2016): 297 buggy student programs in six assignments, each with a blackbox and a whitebox JUnit suite. Repair uses the blackbox suite; the whitebox suite is held out. The converted tests reproduce the dataset's published pass/fail table exactly (33 whitebox-ok, 39 blackbox-ok, 225 fail both). No patch touched the generated test driver. 120 s budget per program.

| Assignment | Fail blackbox | Plausible patch | Also pass all held-out whitebox tests |
|---|---|---|---|
| checksum | 7 | 0 | 0 |
| digits | 51 | 6 | 2 |
| grade | 89 | 5 | 5 |
| median | 51 | 21 | 10 |
| smallest | 47 | 16 | 12 |
| syllables | 13 | 2 | 2 |
| **all** | 258 | 50 | 31 |

The 39 programs that already pass the blackbox suite are returned unchanged. Median time per buggy program: 24.2 s.

## QuixBugs (Java)

`scripts/quixbugs.py`. QuixBugs (Lin et al. 2017): 40 classic algorithms, each with a one-line bug, specified by JUnit tests (258 tests after dropping @Ignore). Each JUnit class becomes a stdin-driven driver that prints the computed values; expected outputs come from QuixBugs' correct versions, and no expected value appears in the file. Because test inputs still live in the driver, every patch is re-run with the repaired program class placed into the original, untouched harness; patches that pass only by editing test code are rejected (the compiler reported success on 16, of which 3 edited test inputs). 120 s budget per program.

| Outcome | Programs |
|---|---|
| Plausible (passes all tests with the untouched harness) | 13 / 40 |
| Identical to the reference fix | 7 |
| Equivalent to the correct version on random inputs | 4 |
| Overfitted (plausible but wrong on other inputs) | 2 |
| **Correct** | **11 / 40** |

- GET_FACTORS: 0/2000 differ (trial division without the sqrt bound: correct, slower)
- LEVENSHTEIN: 0/300 differ (`0 + x` instead of `x`)
- PASCAL: 0/2000 differ (`c <= r` instead of `c < r + 1`)
- QUICKSORT: 0/2000 differ (equal elements sent to the lower partition instead of the upper)
- FIND_IN_SORTED: 253/2000 differ, e.g. empty array: ArrayIndexOutOfBoundsException instead of -1
- MERGESORT: 182/2000 differ, e.g. empty list: StackOverflowError instead of []

## Published baselines on the same benchmarks

RepairThemAll (Durieux et al., ESEC/FSE 2019) ran 11 Java repair tools with a two-hour budget per bug. Patched bugs (plausible patches):

| | IntroClassJava (297) | QuixBugs (40) |
|---|---|---|
| Best single tool | 32 (Nopol) | 4 (ARJA, GenProg-A, RSRepair-A, Cardumen) |
| Union of all 11 tools | 62 | 12 |

The protocols are not identical (test-suite choice, budgets, adapters), so this is an indication, not a controlled comparison.
